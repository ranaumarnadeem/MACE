\begin{abstract}
MACE is an agentic AI system that plans, builds, and verifies multicore OpenPiton configurations on
the CHIA framework. Phase 1 adds \code{chia\_openpiton}, a CHIA adapter for OpenPiton's configure,
build, run, and collect operations, with 209 tests that need no OpenPiton checkout. Phase 2 adds the
MACE loop: a planner breaks a hardware objective into tasks, the tasks run in parallel, and a
deterministic integrator gates every change on Verilator simulation. A failure-analysis agent
diagnoses failures, and the planner replans around them.

We tested MACE against two baselines, manual mesh scaling and a one-shot LLM prompt, on 2x2 and 4x4
meshes, with every result gated by Verilator simulation of the RTL. Besides OpenPiton's Ariane and
OpenSPARC T1 cores, we brought up PicoRV32, fixing two bugs in its OpenPiton integration and enabling
an existing SRAM define. We also traced a Verilator~5 scheduling bug that makes CVA6's cache adapter
drop invalidations, and worked around it with atomic barrier polling. With these changes, MACE's
loop passes 2x2 and 4x4 meshes of both Ariane and PicoRV32, while the one-shot baseline fails every
configuration it attempts.
\end{abstract}

\section{Introduction}

Current agentic coding systems are typically benchmarked on isolated tasks or toy
problems~\cite{humaneval,verilogeval}, which misses the complexity of hardware construction.
Bringing up a multicore system means navigating a large RTL codebase (OpenPiton~\cite{openpiton}
spans hundreds of thousands of lines across network-on-chip, cache-coherence, tile, and platform
logic), a fragile toolchain (version skew, cross-compilation bugs, checkout-specific issues), and
verification that takes minutes to hours per attempt.

MACE is designed for this environment. Given a hardware objective, such as ``bring up a 2x2 mesh''
or ``verify workload $W$ passes,'' MACE plans tasks, builds and simulates each configuration,
diagnoses failures from Verilator~\cite{verilator} output, and iterates. Every result in this paper
comes from Verilator simulation.

\subsection{Features}

MACE contributes:
\begin{itemize}
\item \code{chia\_openpiton} (Section~\ref{sec:phase1}): a CHIA adapter for OpenPiton with a
configure/build/run/collect interface, following the structure of CHIA's ESP adapter.
\item The MACE loop (Section~\ref{sec:phase2}): planning, parallel task execution, deterministic
integration, and LLM-driven failure triage, tested end to end against full Verilator runs, with cost, time, and task
metrics.
\item PicoRV32 support (Section~\ref{sec:pico}), next to Ariane and OpenSPARC T1, from two fixes to
its upstream OpenPiton integration and one existing define.
\item An interactive CLI and Verilator code coverage as a second verification axis
(Section~\ref{sec:cli}).
\end{itemize}

\section{Background}

CHIA~\cite{chia} provides the agent, tool, and dispatch layer this project builds on: colocated
resource-pinned worker nodes, an LLM abstraction layer spanning multiple backends, and
Ray-based~\cite{ray} remote dispatch and caching. OpenPiton~\cite{openpiton} is Princeton's
open-source, silicon-proven manycore research framework; Figure~\ref{fig:tile} shows a mesh and one
of its tiles. Its three tile cores, the latter two added through BYOC~\cite{byoc}, are OpenSPARC T1
(\code{sparc}), Ariane/CVA6~\cite{cva6} (\code{ariane}), and PicoRV32~\cite{picorv32}
(\code{pico}). Before this project, CHIA had no OpenPiton adapter.

\textbf{Related work.} LLM-based hardware design has mostly been evaluated at module scale.
VerilogEval~\cite{verilogeval} scores single-module Verilog generation, ChipNeMo~\cite{chipnemo}
adapts LLMs to chip-design tasks, and AutoChip~\cite{autochip}, RTLFixer~\cite{rtlfixer},
VerilogCoder~\cite{verilogcoder}, and MAGE~\cite{mage} feed compiler or simulation results back to
one or more agents to repair generated RTL. In software, SWE-bench~\cite{swebench} moved evaluation
from isolated functions~\cite{humaneval} to repository-level issues. \sys{} applies the same
agent-with-feedback idea at system scale: it plans and verifies bring-up of an existing manycore,
gated by whole-system Verilator simulation.

\section{Phase 1: The OpenPiton Adapter}
\label{sec:phase1}

\textbf{Design.} Figure~\ref{fig:arch} shows where the adapter sits. \code{OpenPitonWorkspaceNode} is
a CHIA \code{ColocatedNode} whose resource-pinned remote functions configure, build, run, and
collect results. OpenPiton writes generated \code{.tmp.v} files into its source tree on every build,
so each worker gets its own checkout, reserved through one \code{openpiton} resource unit. Pure
parsers read verdicts from OpenPiton's transcripts, using the strings its RTL monitors emit.

\textbf{Results.} The adapter's 209 tests that need no OpenPiton checkout all pass, and so do
acceptance tests with full Verilator builds, including two checkouts building in parallel: 176s
versus 324s serial. One acceptance test, 2x2 Ariane on a GCP worker, remains blocked by unreliable
dispatch to that worker (Section~\ref{sec:limits}).

\section{Phase 2: The \sys{} Loop}
\label{sec:phase2}

\textbf{Pipeline.} Figure~\ref{fig:pipeline} shows the loop. A planning agent turns a
\code{MaceSpec} (core, target mesh, gate workloads, objective, budget) into a task DAG, and workers
dispatch ready tasks in parallel through Ray, each pinned to its own checkout
(Figure~\ref{fig:arch}). A deterministic
integrator runs the tasks in dependency order: each builds its own configuration, including any
cache or RTL-define overrides the planner gave it, and runs the first gate workload, whose
\emph{verdict}, parsed from simulator output, must read \code{pass}. On
a failure, a failure-analysis agent with read-only tools (log grep, file collection, a fixture
diff, and an \code{objdump} symbol check) diagnoses the transcript, and the planner replans around
its proposed fix.

\textbf{Gate workloads surface a memory-visibility bug.} Writing the gate workloads
(barrier-and-atomic-counter, producer/consumer, hart-id scatter/gather) showed that a plain
\code{volatile} read of a shared value was not reliably visible from the same hart shortly after the
write, while an atomic fetch-and-add-zero read always was. Every gate workload now reads shared values through this
\code{atomic\_read()} helper.

\textbf{Resource enforcement.} \sys{} checks all three \code{Budget} dimensions (iterations, USD,
wall-clock) before each iteration starts. The USD check reads zero on Vertex, because CHIA's Vertex
backend reports no price (Section~\ref{sec:cost}). \sys{} verifies the checksums of its C gate
programs before any LLM call or checkout access.

\section{Adding PicoRV32}
\label{sec:pico}

Each core reaches its tile's L1.5 through its own adapter (Figure~\ref{fig:tile}), and a core with its
own coherent cache, as Ariane has, needs new coherence-adapter RTL. PicoRV32 has no such cache and
already has an upstream transducer, which OpenPiton's CI builds under Verilator but never runs.

Our first pico runs built but never reached a trap. Tracing them found two bugs and one setting
(\mk{2}, \mk{3}): the core's self-boot gate, the monitor's tracking of pico's tile, and an SRAM
power-on self-clear that discarded pico's first memory writes, which an existing OpenPiton define
turns off. With these changes, PicoRV32 passes under Verilator on 2x2 and 4x4 meshes, every tile reaching \code{Hit Good trap} on \code{addi.S}. Its
OpenPiton integration has no C compiler, so it runs assembly workloads only.

\section{Additional Capabilities}
\label{sec:cli}

\sys{} has an EDA-style interactive shell, modeled on Yosys and OpenROAD, that checks core
compatibility before a run. For a second verification axis, we patched the OpenPiton testbench to
call Verilator's coverage-write API: a 2x2 Ariane run covers 9497 of 26900 lines (35.3\%). The loop
reaches its LLM through CHIA's backends; every result in this paper used Vertex with Gemini~2.5~Flash.

\section{Evaluation}
\label{sec:eval}

We compare three approaches on 2x2 and 4x4 meshes: \textbf{(a)} manual mesh scaling with a time
log, \textbf{(b)} a single LLM prompt for a configuration, built and run once with no tools and no
retry, and \textbf{(c)} the full \sys{} loop, with every LLM call on Gemini~2.5~Flash
(Table~\ref{tab:eval}). Ariane runs \code{barrier\_atomic.c}; pico runs \code{addi.S}, since its
integration has no C toolchain; SPARC does not yet run under our Verilator (Section~\ref{sec:limits}).
All three approaches get pico's \code{CONFIG\_DISABLE\_BIST\_CLEAR} define: (a) sets it by hand,
and the objectives for (b) and (c) name it; (b)'s config line accepts RTL defines, and (c)'s planner
requests one through a new \code{CONFIG\_RTL:} directive, which adds it on top of the mesh's defaults.

(b) fails every configuration. In three of four, \code{PitonConfig}'s construction-time validation
rejected the LLM's config before any build: it set the L1.5 size to zero, which every OpenPiton tile
needs, and (b) has no retry path. On pico it included the named define both times. At ariane 4x4 it
chose oversized caches, including a 4\,MB L2 per tile: the build took 35 minutes and the simulation
timed out with no tile finished. The two prompts differ: the planner's lists the default cache sizes
and requires positive values, and the planner falls back to the defaults on a malformed cache line.
The one-shot prompt has neither.

\textbf{Mesh scaling to 2x2 and 4x4.} Manual scaling (a) first stalled at 2x2 and never reached 4x4,
for two reasons. Under Verilator~5, a known scheduling bug~\cite{verilator5829} makes CVA6's L1.5
adapter drop cache invalidations (\mk{1} in Figure~\ref{fig:tile}), so the plain-load exit barrier in \code{syscalls.c} never sees other
tiles' updates; OpenPiton pins a CVA6 that predates the upstream workaround~\cite{cva6pr2809}.
A hand port of that workaround passes 2x2 with the unmodified barrier (4 of 4 tiles, 24s), while the
original adapter times out with one tile done. Separately, the monitor's 32-bit \code{finish\_mask}
(\mk{3}) capped verification at 8 tiles. Our runs keep the pinned adapter, poll the barrier with
atomic reads, and widen the mask. With both in place, manual runs pass both sizes, and the loop planned
and verified both meshes, every tile confirmed, with no changes to its planning or verification logic
(Table~\ref{tab:eval}): 2x2 in 750.1s across four tasks, including an L1D-associativity variant the
planner chose to verify, and 4x4 in 250.9s on a cached build. On pico it passes in a single task at
both sizes, the 4x4 run also on a cached build.

\textbf{Recovery.} The detect, diagnose, and replan cycle is exercised only at the mechanism level,
with a stub that fails once and then passes; no passing run above needed it. Its one live failure, a
pico 4x4 build cached before the \code{finish\_mask} fix, went unrecovered: the build ID covers only the
configuration, so all three iterations reused that stale build, and triage never identified it. A
clean rebuild passed.

\section{Cost}
\label{sec:cost}

All experiments behind this paper cost \$37 of a \$300 GCP credit allocation, covering simulation
compute and LLM inference; development used a \$20/month Claude subscription, outside that budget. We built \sys{} and drafted
this paper and its documentation with Claude Code, and we reviewed all text and results.
A single loop run is cheap. At 2x2, an ariane run costs about \$0.12 (\$0.04 of LLM tokens and
\$0.08 of compute) and a pico run about \$0.02, while a sparc run that exhausts its three-iteration
budget would cost an estimated \$0.25, mostly for its one-time build. We estimate compute as
\code{e2-highmem-8} time (\$0.36/hour) over each run's wall time, and tokens at Gemini~2.5~Flash's
\$0.30 and \$2.50 per million input and output tokens. \sys{}'s own cost counter reads zero because
CHIA's Vertex backend reports no price and omits thinking tokens, more than half of the billed output
here, so we measured tokens by re-sending representative planner and task prompts.

\section{Limitations and Future Directions}

\subsection{Limitations}
\label{sec:limits}

OpenSPARC T1 builds but does not run under our Verilator~5.020: the core never receives its power-on
wake-up interrupt. OpenPiton's own CI recipe stalls the same way here, while CI uses Verilator~4, so
the cause is environmental; it remains open. Dispatch to a tailnet-relayed GCP worker is also
unreliable: exporting the proxy variables \code{chia up} sets fixed a first hang, but a later attempt
hung again with no outbound traffic, pointing at Ray's scheduling under a proxied topology.

In the reported runs, the LLM decides the task list, cache sizes, and RTL defines; task agents get
no tools, and we wrote every RTL and testbench fix in this paper. Each Table~\ref{tab:eval} cell is
a single run on one checkout. The Nix flake pins Verilator~5.052, while the reported runs used 5.020.

\subsection{Future Directions}

All three cores already had upstream adapters to the L1.5; a core without one, such as Ibex or
Rocket Chip, needs it written first. The next step is a reusable adapter template built from the
shape the three share (a per-core RTL directory, a transducer, and a core-select arm in the tile
template), with \sys{}'s loop verifying each revision of the adapter RTL in Verilator as an engineer
writes it. A dashboard over the run database would show dispatch, build, and verification live.

\balance
\section{Conclusion}

\sys{} shows that an agentic loop can plan, build, and verify multicore hardware, with every result
gated by RTL simulation. Along the way we fixed RTL and testbench bugs and added PicoRV32 next to
Ariane and OpenSPARC T1, and the loop then passed 2x2 and 4x4 meshes of both Ariane and PicoRV32. The next steps are a reusable
adapter template for new cores and a recovery cycle proven on live failures.
