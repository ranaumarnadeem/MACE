\small\textbf{Abstract.}
\sys{} (Multi-core Agentic Co-design Engine) is an agentic AI system for autonomous multicore
hardware construction and verification, built on Google/NVIDIA's CHIA framework. Phase~1
contributes \code{chia\_openpiton}, a CHIA platform adapter exposing OpenPiton's
configure/build/simulate/run/collect operations through CHIA's standard interface, validated
against real RTL simulation across 143 tests. Phase~2 contributes the \sys{} loop itself: a
planner decomposes a hardware objective into a task DAG, specialized agents execute tasks in
parallel, a deterministic integrator applies and gates every change against real Verilator
simulation, and a failure-analysis agent triages and replans on any failure. We evaluate \sys{}
against two baselines -- manual mesh scaling and a single-shot LLM configuration with no tools or
iteration -- across all three supported cores, using real hardware runs throughout, with no
simulated results anywhere in this paper. We report what worked, what did not, and precisely why: a
genuine RTL-level finding while extending \sys{} to a third, never-before-simulated core (PicoRV32);
a real dispatch failure against a dependency we do not control (CHIA's tailnet-relay task
launching), first misdiagnosed as a scheduler bug and corrected once better evidence arrived; a
one-shot LLM baseline that fails on all three cores in three distinct ways, where \sys{}'s loop
passes on one and, on the other two, correctly exhausts its retry budget rather than reporting a
false pass; and two real mesh shapes (2x2, 4x4) where manual scaling got stuck but the full loop
passed.

\section{Introduction}

Agentic coding systems are increasingly evaluated on isolated, synthetic tasks: a single file, a
single test, a sandboxed toy problem. Real hardware construction rarely looks like that. A real
multicore system means a large, real RTL codebase (OpenPiton spans hundreds of thousands of lines
across network-on-chip, cache-coherence, tile, and platform logic), a toolchain with real,
non-obvious failure modes (version skew, cross-compilation quirks, checkout-specific bugs), and
verification costing real minutes to hours per attempt, not milliseconds.

\sys{} targets exactly this harder, more realistic setting. Given a hardware objective -- ``bring
up a 2x2 mesh,'' ``verify workload $W$ passes'' -- \sys{} autonomously plans, implements, builds,
simulates, diagnoses failures against real Verilator output, and iterates, with every claim of
success gated by an actual passing RTL simulation rather than a self-report from an agent.

This paper makes four contributions:

\begin{enumerate}
\item \textbf{\code{chia\_openpiton}} (\S\ref{sec:phase1}), a CHIA platform adapter for OpenPiton
exposing a full configure/build/run/collect interface, following the same abstraction CHIA already
uses for its gem5 and ESP adapters, so it is directly upstreamable.
\item \textbf{The \sys{} loop} (\S\ref{sec:phase2}): planning, parallel task execution,
deterministic integration and gating, and LLM-driven failure triage, evaluated end-to-end against
real hardware with real cost, time, and task-count metrics.
\item \textbf{An extension exercising the adapter's generality} (\S\ref{sec:pico}): adding
PicoRV32 as a third supported core, which surfaced a genuine, previously unknown finding about
PicoRV32's own OpenPiton integration -- one that nobody, including OpenPiton's own continuous
integration, had ever observed, because nobody had ever run it under a simulator before.
\item \textbf{A production interface and two new capabilities} (\S\ref{sec:cli}): a real
interactive CLI, a second verification axis (real Verilator code coverage, not just pass/fail),
and a second LLM backend proven end-to-end, none of which the original proposal required.
\end{enumerate}

\section{Background}

\textbf{CHIA} provides the agent/tool/dispatch substrate this project builds on: colocated
resource-pinned worker nodes, an LLM abstraction layer spanning multiple backends, and a
Ray-based remote-dispatch and caching mechanism. \textbf{OpenPiton} is Princeton's open-source,
silicon-proven manycore research framework: tiles connected by a 2D-mesh network-on-chip, each
speaking a proprietary MESI-coherence-aware protocol (L15, descended from OpenSPARC T1's PCX/CPX
bus) to reach the NoC. OpenPiton historically supports three tile cores: OpenSPARC T1
(\code{sparc}), Ariane/CVA6 (\code{ariane}, RV64GC, coherent), and PicoRV32 (\code{pico}, RV32I,
non-coherent). Before this project, CHIA had no OpenPiton adapter at all.

\section{Phase 1: The OpenPiton Adapter}
\label{sec:phase1}

\textbf{Design.} \code{OpenPitonWorkspaceNode} is a CHIA \code{ColocatedNode} exposing
\code{configure}, \code{build}, \code{run}, \code{regress}, \code{collect}, and \code{clean} as
resource-pinned remote functions. OpenPiton's own template preprocessor writes generated
\code{.tmp.v} files directly into the source tree on every build, so concurrent builds must never
share a checkout -- the adapter reserves one \code{openpiton} resource unit per checkout, and
parallel work is achieved by giving each worker its own checkout rather than by locking inside a
shared one. Pure parsers extract build/run verdicts directly from OpenPiton's own simulation
transcripts (\code{sim.log}, \code{status.log}) using the exact strings OpenPiton's own RTL
monitors emit, so a verdict is never inferred from an agent's own claim.

\textbf{Real hardening.} Getting real hardware to build at all surfaced four permanent,
environment-level bugs, fixed once in a single idempotent patch script: binutils~2.38+ splitting
\code{zicsr}/\code{zifencei} out of base RV64I (breaking the boot ROM's own assembly), GCC~15's C23
default breaking a legacy two-argument function call, broken git symlinks on a Windows-mounted
checkout materializing as literal path-text files, and 66 CRLF-terminated shebang lines. None are
\sys{}-specific -- friction any real deployment of decades-old RTL encounters.

\textbf{Build-result caching.} \code{build()} skips re-invoking the simulator entirely when a
matching successful-build marker already exists on disk. Measured on a real rebuild of an
identical configuration: 104s~$\rightarrow$~0.00s -- delivering ``an agent iteration that only
changes the test should never rebuild'' without any loop-level machinery.

\textbf{Results.} 143 tests across three tiers (pure-unit, live-Ray with a stub simulator, and
real hardware) all pass. Real-hardware acceptance tests pass for a 1x1 Ariane build and run
(\code{hello\_world.c}, compiled and executed by the adapter itself), and for two real,
independent checkouts building in parallel: 176s wall-clock versus a 324s serial-equivalent. Only
one acceptance test -- 2x2 Ariane on a real GCP worker -- remains blocked, on infrastructure
outside this project's own code (\S\ref{sec:limits}).

\section{Phase 2: The \sys{} Loop}
\label{sec:phase2}

\textbf{Pipeline.} Figure~\ref{fig:pipeline} shows the full loop. A
planning agent turns a \code{MaceSpec} (core, target mesh, gate workloads, objective, budget) into
a task DAG; workers dispatch dependency-satisfied tasks in parallel via Ray, each pinned to its own
checkout. A deterministic integrator -- no LLM in this step -- applies accepted diffs to the
canonical tree in dependency order, then fans real build-and-run out across every gate workload.
The gate is binary and non-negotiable: every workload's \emph{verdict}, parsed from real simulator
output, must read \code{pass}. On any failure, a failure-analysis agent (restricted to read-only
inspection tools -- grep, status, collect) diagnoses the transcript and proposes a fix; the planner
replans around it.

\textbf{Gate workloads found a real bug of their own.} Writing the deterministic gate workloads
(barrier-and-atomic-counter, producer/consumer, hart-id scatter/gather) surfaced a genuine
memory-visibility issue on this RTL/toolchain combination: a plain \code{volatile} read of a shared
\emph{array element} was not reliably visible even from the same hart shortly after the write,
while the identical value read back through an atomic fetch-and-add-zero always was. Every gate
workload now routes shared reads through this \code{atomic\_read()} helper -- a workload-development
finding, not a claim about the loop's own failure-recovery behavior.

\textbf{Enforcement, not just measurement.} All three \code{Budget} dimensions -- iteration count,
USD, wall-clock -- are checked before each iteration starts, not merely logged afterward.
Gate-workload checksums are verified at run start, before any LLM call or checkout is touched, so a
task cannot tamper with its own grading.

\textbf{Replay, scoped honestly.} LLM, build, and run decisions are cache-tagged and re-served at
zero additional token or compute cost. Verified directly, by reading CHIA's own cache/bypass
implementation, that this reproduces \emph{decisions} (an LLM's response text, a build/run's
pass/fail artifact) -- not the literal source edits an agent made through its tools; those remain
git's job. An honest, useful scope, not a shortcoming to paper over.

\section{A Third Core: PicoRV32}
\label{sec:pico}

We were asked whether \sys{} could take arbitrary core RTL plus a specification and integrate it
into OpenPiton's multicore fabric automatically. Investigating before writing any code, we found
this framed the problem incorrectly: OpenPiton has no reusable core-to-NoC bridge at all. Each core
has its own bespoke L15 adapter; even Ariane's own AXI4 output is never touched, since a
hand-written encoder taps CVA6's internal pre-AXI cache-miss stream instead. The real dividing line
is not ``does the core speak a standard bus'' but ``does the core have a coherent cache of its
own'' -- Ariane's situation needs genuine new coherence-adapter RTL, well outside our remaining
time budget. PicoRV32's situation is different: a complete, upstream, TODO-free adapter
(\code{pico\_l15\_transducer.v} and friends) already exists, fully instantiated in OpenPiton's own
tile generation logic -- it has simply never been \emph{run} under any simulator, by anyone.
OpenPiton's own CI builds it under Verilator but its run job is commented out, targets a
nonexistent stage, and even when live specified a different simulator entirely.

\textbf{Toolchain reuse, confirmed not assumed.} We found that the RV32IMA/ILP32 multilib already
present in our installed \code{riscv64-unknown-elf-gcc} covers PicoRV32 with zero new toolchain
installation -- confirmed with a real trial assemble-and-link of the target diagnostic, not merely
by checking multilib metadata.

\textbf{Results.} The adapter extension (a new \code{Literal} entry, two \code{sims} flags, and
mirrored tests) landed with full unit coverage and zero regressions to the existing \code{ariane}
and \code{sparc} paths. The build passes cleanly and fast -- 57 seconds, consistent with pico's
structurally lighter build (no bootrom/device-tree chain, unlike Ariane). The run reaches verdict
\code{maxcycles}.

The compiled binary's symbol table and entry point exactly match the run's own configured trap
addresses (\code{objdump~-t}/\code{-f} against \code{symbol.tbl}). Comparing the run's transcript
against a known-good passing-Ariane fixture from earlier in this project: both show an
\emph{identical} generic boot/reset/IOB-handshake trace -- but the fixture's very next line,
\code{Hit Good trap}, never appears for pico. This localizes the
divergence precisely: not boot infrastructure, not the compiled binary, but the point at which the
core itself must reach its own trap address. Unsurprising, in one sense -- nobody has ever run this
core under a simulator before to catch it -- and exactly the property originally asked for: \sys{}
distinguished ``builds'' from ``runs correctly'' instead of reporting a false pass.

\section{Beyond the Proposal: Interface, Coverage, Portability}
\label{sec:cli}

Three capabilities beyond the original proposal, each proven against real hardware or a live
backend, never a mock.

\textbf{The \code{mace} CLI}, a Yosys/OpenROAD-style interactive shell
(\code{read\_verilog}/\code{top\_module}/\code{read\_spec}/\code{set\_core}, then \code{run}), is
the actual interface a user drives \sys{} through, not just an API. When \code{top\_module} names
no core \code{chia\_openpiton} has an adapter for, \code{run} immediately produces the same
structured assessment \S\ref{sec:pico} needed real investigation to first establish, instead of
attempting a fake integration.

\textbf{Verilator code coverage} (\code{run -coverage}) is a second verification axis beyond
pass/fail, and needed a genuine fix, not just a flag: OpenPiton's own hand-written testbench never
called Verilator's coverage-write API, so a clean run produced no data until patched. A real run
(1x1 Ariane, \code{barrier\_atomic.c}) reports 36.00\% (8787/24311) -- hardware-measured.

\textbf{Backend portability}: the \sys{} loop runs end-to-end, unmodified, against Google's Vertex
Gemini backend as well as OpenCode, confirmed with a full real passing run. Vertex authenticates via
Application Default Credentials rather than a literal key, and required identifying which model was
actually available on our project (\code{gemini-2.0-*} 404s; \code{gemini-2.5-flash} works).

\section{Evaluation}
\label{sec:eval}

We compare three approaches: \textbf{(a)} manual mesh scaling with a time log; \textbf{(b)} a single
LLM prompt asking directly for a configuration, applied once with no tools, no verification, and no
retry; \textbf{(c)} the full \sys{} loop. All results below are real hardware runs -- no simulated
numbers appear anywhere in this paper.

\textbf{Three cores, two baselines.} (b) and (c) were run against the identical objective (verify
\code{barrier\_atomic.c} on a 1x1 mesh) for all three supported cores, not just ariane, same LLM
backend (Gemini~2.5~Flash) throughout (Figure~\ref{fig:eval}, left).

(b) fails all three, in three distinct ways -- each itself informative. For ariane, the one-shot
config built but failed real verification: a functionally wrong guess. For sparc, it built and even
reached a run attempt that then failed silently, no verdict at all. For pico, the LLM's own proposed
config (\code{l15\_size=0}) was rejected by \code{PitonConfig}'s own construction-time validation
before any hardware was touched -- (b)'s script has no retry path for a malformed response. (c)
passes ariane (4/4 tasks, 741.7s, roughly 4x (b)'s cost -- not ``for free'' as an earlier, buggy
measurement implied); a second, distinct ariane gate workload, \code{producer\_consumer.c}, also
passed (2118.02s, 2 tasks) -- real coverage beyond one program, not repeated success on the same
one. For sparc and pico, (c) does not pass either -- but its own triage/post-mortem,
not us reading logs by hand, told the two failures apart correctly: sparc's 3 replan attempts still
could not resolve a missing \code{util.h} include path in the gate program's own build (classified
\code{fixable\_config}, an LLM diagnosis we have not independently verified); pico's 3 attempts all
deadlocked (\code{maxcycles}) because \code{barrier\_atomic.c}'s own barrier logic needs more than
one participant -- something a 1x1 mesh can never provide -- correctly classified
\code{likely\_hardware\_limitation} (more precisely a workload/mesh mismatch, not a regression of
the pico RTL bugs \S\ref{sec:pico} already fixed).

\textbf{The loop recovers mesh shapes manual scaling could not.} Baseline~(a)'s own real attempts
got stuck at 2x2 (build passes, run hangs) and never reached 4x4 -- see \S\ref{sec:limits} for the
two real, independent causes behind that. The full loop, same mesh shapes, real hardware, passed
both (Figure~\ref{fig:eval}, right).

Phase~2's own fan-out (two real tasks, two checkouts, gated through baseline~(c)'s own path)
measured 30s parallel vs.\ 57s serial, consistent with Phase~1's result above.

One honest gap: the detect-failure~$\rightarrow$~diagnose~$\rightarrow$~replan~$\rightarrow$~pass
cycle is proven at the mechanism level (a stateful stub that fails once, then passes) but never
fired across the passing hardware runs above -- including a forced extreme first configuration (a
128-byte, direct-mapped L1, confirmed actually used) that we and the planner both expected to fail.
It passed instead: a genuine finding about this RTL's coherence robustness to cache-capacity
extremes, not a test-design failure, reported as such rather than letting repeated passes imply more
than they show.

\section{Limitations and Honest Findings}
\label{sec:limits}

\textbf{A launch-configuration gap we first misdiagnosed as a CHIA scheduler bug -- corrected once
better evidence arrived.} A task whose resource request could only be satisfied by a tailnet-relayed
GCP worker never executed, though that worker's own registration and heartbeat to the cluster's GCS
worked fine throughout. We ruled out a worker-startup failure (node stayed \code{Alive} with correct
resources) and scheduler slowness (a six-minute state-dump showed zero pending start requests),
initially concluding this was a genuine gap in CHIA's own scheduling/relay plumbing and filing it
upstream (\texttt{ucb-bar/chia\#72}) rather than guessing at a fix. A CHIA maintainer's reply
identified the real cause: CHIA sets three proxy environment variables on each node during
\code{chia up}, inherited by a job submitted via \code{chia job submit} but not by a driver launched
manually via \code{python driver.py} -- what every real run here does -- unless the launching shell
sets them itself. Verified directly: exporting the exact values read off the head's own live raylet
took the same forced-placement task from a six-minute hang to a two-second real execution. Every
fact we found was correct; the conclusion was not -- corrected here rather than left standing. With
dispatch fixed, 2x2 Ariane on GCP still has not reached a verdict -- a build-time worker crash,
likely the same memory-pressure class as below.

A later, independent dispatch attempt on the same topology reproduced the stuck symptom -- this
time with the environment fix already confirmed in place, ruling out a repeat of the same cause.
Both tailnet relays' logs show zero new activity during the stall, and \code{strace} on both raylets
shows zero new \code{connect()} syscalls -- real, continuous traffic on already-established
connections, just nothing new. Whatever carries a lease assignment from the GCS to this worker's
raylet appears to never attempt an outbound connection at all -- Ray's own scheduling internals
under a proxied topology, not a CHIA gap. Filed as a follow-up on the same upstream issue; open at
time of writing.

\textbf{Two RTL-adjacent hangs, read as genuine gaps rather than our bugs.} Both the 2x2 Ariane mesh
and the 1x1 PicoRV32 run show an identical signature: a correct boot/reset/IOB handshake, then the
core never reaches its own trap address, despite correct compiled binaries. OpenPiton's own CI shows
2x2 Ariane has no upstream Verilator precedent besides 1x1 and 4x4, and PicoRV32 has never run under
any simulator, by anyone. We read both as likely, previously-undiscovered RTL gaps in untested
configurations, not adapter bugs -- the same code drives the passing cases -- but did not chase
either to a waveform-level root cause given the time left.

\textbf{4x4 memory pressure, two independent causes, both diagnosed precisely.} The one
upstream-validated mesh shape (4x4) surfaced two real, independent memory-pressure failures: a
genuine Ray-reported OOM (22.33GB/23.47GB used) from unconstrained parallel compilation, fixed via
\code{MAKEFLAGS}; and, separately, Verilator's own build step passing an explicit, unlimited
\code{-j} directly on its command line, silently overriding that fix. Both evidenced via direct
\code{/proc} inspection -- host-local findings, not a design flaw in \sys{}. A later, solo attempt
via the full loop passed instead (Figure~\ref{fig:eval}, right, 574.6s), consistent with the OOM
above, specifically from concurrent compilation this later run never exercised.

\enlargethispage{\baselineskip}
\section{Conclusion}

\sys{} shows an agentic loop can autonomously plan, build, and verify real multicore hardware,
gated by real RTL simulation, not an agent's word. It fixed environment bugs, added a third core,
and verified mesh shapes never reached before -- precision, not one pass, is the contribution.
